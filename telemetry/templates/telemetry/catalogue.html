WIS2 Alert Documentation

A comprehensive reference for the WIS2 Monitoring Events (WME) framework, covering infrastructure diagnostics, schema validation, systemic telemetry, and actionable response strategies. Based on the WMO WIS2 Monitoring Events specification and empirical telemetry analysis.

◆

1. Introduction to the WIS2 Observability Framework

The transition of the World Meteorological Organization (WMO) to the Information System 2.0 (WIS2) represents a fundamental architectural evolution. Moving away from the legacy, point-to-point file exchange mechanisms characteristic of the Global Telecommunication System (GTS), WIS2 embraces a highly available, globally distributed Publish/Subscribe (PubSub) architecture.

This modern paradigm relies upon a synergistic network of core infrastructure components known as Global Services:

  • Global Brokers — message routing
  • Global Caches — data payload hosting
  • Global Discovery Catalogues (GDCs) — centralized metadata querying and discoverability
Performance Mandates

Global Brokers must achieve at least 99.5% service availability, process a minimum of 10,000 messages per second, and seamlessly support hundreds of concurrent WIS2 Nodes.

The WME specification mandates the use of the CloudEvents standard, encoded in JSON, broadcast over a dedicated MQTT topic hierarchy — specifically monitor/a/wis2/# — allowing Global Services and monitoring agents to continuously ingest state changes, error reports, and system health metrics. Through this mechanism, the WMO has established a real-time diagnostic nervous system capable of identifying everything from localized network timeouts to global schema validation failures.

MQTT Topic Hierarchy

Agents subscribe to channels such as monitor/a/wis2/+ (all centers) or monitor/a/wis2/ca-eccc-msc/# (center-specific), constructing a continuous, real-time topology of network health without generating polling overhead.

⚙

2. Architectural Anatomy of WME

WIS2 Monitoring Event Messages (WMEM) are strictly bounded by the http://wis.wmo.int/spec/wme/1/req/monitoring-event-message-core requirement class. Metadata payloads must not exceed 8,192 bytes.

PropertyTypeDescription
id UUIDv4 Unique event identifier. Prevents message collision and enables chronological tracing across distributed log aggregators.
type String (Reverse DNS) Defines the nature of the anomaly (e.g. int.wmo.wis.wme.event.wcmp2.ets, int.wmo.wis.wme.wnm.validation.schema).
source String The specific agent or monitoring service that detected the anomaly.
subject String Identifies the failing or notifying entity (the node being observed).
data.severity Enum Strictly enumerated: DEBUG, INFO, WARNING, ERROR, CRITICAL.
data.content Object Human-readable diagnostic summaries.
data.links Array Machine-actionable endpoints for querying related metadata or documentation.

Severity Levels

Every alert is assigned a severity level reflecting the urgency and impact of the issue.

SeverityMeaningTypical Actions
CRITICAL Systemic or total blackout. Node disconnected from all brokers, cache receiving zero bytes, target endpoint down. Immediate attention required. Engage emergency fallback. Reroute to backup caches/brokers. Page standby engineers. Escalate to hardware/ISP level. Extensive postmortem upon restoration.
ERROR Isolated failure affecting specific data sets. WNM schema failure, HTTP 403/502, missing metadata, connection refused. Node is reachable but producing errors. Quarantine malformed payload. Suspend downstream fetching. Alert data provider immediately. Require manual schema correction or WAF ACL whitelisting.
WARNING Degradation of redundancy or creeping friction. Disconnected from one broker, KPI score dipping, download errors. System is functional but degraded. Trigger automated network diagnostics (traceroute, ping). Verify TLS certificates. Log non-urgent ticket for next-business-day review.
INFO Non-disruptive routine telemetry. WCMP2 ETS passed, standard heartbeats, metadata reports. No immediate action required. Ingest to time-series databases for long-term SLA reporting. Used by Sensor Centres to tune KPI algorithms and baseline anomaly detection thresholds.

3. Node Connectivity & Broker Disconnections

A foundational requirement of the WIS2 architecture is that every data-producing Node must maintain continuous, concurrent MQTT connections to multiple Global Brokers. This redundant mesh ensures that if one broker experiences a localized outage, WIS2 Notification Messages (WNMs) are still successfully routed through alternative paths.

Event TitleSeverityEvent TypeCore System Impact
Disconnected WIS2 Node from one Global Broker WARNING int.wmo.wis.wme.event Redundancy degradation; no data loss.
Disconnected WIS2 Node from multiple Global Brokers ERROR int.wmo.wis.wme.event Severe redundancy loss; elevated latency risk.
Disconnected WIS2 Node from all Global Brokers CRITICAL int.wmo.wis.wme.event Complete notification blackout; global data isolation.
Target is down CRITICAL int.wmo.wis.wme.event Node endpoint entirely unreachable for monitoring.

3.1 Degradation of the Broker Redundancy Mesh

"Disconnected WIS2 Node from one Global Broker" — WARNING

Trigger: Global Monitor detects that the continuous heartbeat (or underlying TCP socket state) of a specific WIS2 Node has dropped from one of its configured target Global Brokers while remaining active on the others.

Technical causes: Transient network routing anomalies across international submarine cables; firewall misconfigurations blocking outbound traffic on port 8883 (MQTTS) or port 443 (WSS); or localized TLS handshake failures due to geographic load-balancing discrepancies.

Impact on data flow: Negligible — inherent redundancy ensures WNMs are successfully published via the remaining connected brokers.

Response: Network engineering teams review outbound firewall rules and perform diagnostic packet tracing to the specific disconnected broker.

"Disconnected WIS2 Node from multiple Global Brokers" — ERROR

Trigger: Simultaneous connection drops across two or more (but not all) Global Brokers.

Technical causes: Regional internet backhaul outages; BGP route flapping affecting multiple international transit paths; or resource starvation within the Node's message queue client causing aggressive termination of parallel connection threads.

Impact: While some redundancy remains, data flow is characterized by increased notification latency, and the Node operates precariously close to a total blackout.

Response: Immediately escalate to the Node operator's local network engineering team to inspect edge router stability, outbound connection limits, and CPU utilization of the publishing daemon.

3.2 Total Isolation and Endpoint Failure

"Disconnected WIS2 Node from all Global Brokers" — CRITICAL

Trigger: Global Monitor registers absolute silence from the Node; zero active MQTT connections across the entire Global Broker mesh.

Technical causes: Catastrophic failures — total facility power loss, complete physical isolation from ISPs, expiration of top-level TLS certificates, or fatal runtime crashes within the messaging software (e.g. wis2box).

Impact: Absolute — no WNMs can be published; the global community remains entirely unaware of any new meteorological data generated by the Node, effectively erasing its real-time scientific contribution.

Response: Immediate out-of-band communication with the Node administrator; emergency restarts; physical verification of core internet connectivity.

"Target is down" — CRITICAL

Example targets: wis2.ncm.gov.sa:443, www.wis-jma.go.jp:443

Trigger: Active health checks (HTTP GET requests or ICMP pings) fail to receive any response.

Technical causes: Reverse proxy crashes (e.g. Nginx or HAProxy), DDoS mitigation hardware aggressively blackholing traffic, or total server hardware failure.

Impact: Extends beyond notification failure — the endpoint hosting the actual data payload or metadata services is completely inaccessible.

Response: Local system administrators verify edge load balancers, web server daemons, and physical server availability.

4. Global Cache & Data Flow Disruptions

While Global Brokers manage the signaling and notification pathways, Global Caches are responsible for the heavy lifting of payload distribution. When a WNM announces new data, Global Caches download the data payload from the origin WIS2 Node's HTTP server and cache it locally. End-users then download data from the Cache, shielding the origin Node from overwhelming concurrent bandwidth requests.

Anomalies in this domain signify a critical breakdown between the notification phase and the actual data retrieval phase — data is announced but physically unobtainable.

Event TitleSeverityEvent TypeCore System Impact
No cache is receiving data from that center over the last 6 hours ERROR int.wmo.wis.wme.event.item.download Global "ghosting" effect; data announced but inaccessible.
No data is received from that center over the last 6 hours WARNING int.wmo.wis.wme.event.item.download Potential localized cache failure or slow data production.
The Global cache is not receiving any data since 1 hour CRITICAL int.wmo.wis.wme.event.item.download Cache-wide ingestion failure; broad data staleness.
Global cache has > 10 download errors from center in 1h over 6h WARNING/ERROR int.wmo.wis.wme.event.item.download High friction data fetching; partial payload loss.
Global Cache cannot connect to > 10 (or 20) dataservers ERROR/CRITICAL int.wmo.wis.wme.event.item.download Cache egress failure; inability to populate cache inventory.

4.1 Ingestion Failures and the "Ghosting" Phenomenon

"No cache is receiving data from that center over the last 6 hours" — ERROR

Trigger: Time-series aggregation confirming that for a continuous six-hour window, WNMs are being successfully published by the origin Node, but zero bytes of the associated payload data have been successfully ingested by any Global Cache.

Technical causes: The origin Node publishes valid MQTT notifications, but the canonical HTTP links embedded within those WNMs point to an inaccessible data server — hidden behind a private NAT firewall, DNS misconfigured or not propagated globally, or the HTTP daemon serving physical files has crashed while the MQTT publishing script continues to run.

Impact: Severe "ghosting" — automated subscriber pipelines receive notifications of new weather data, but subsequent programmatic download attempts encounter dead links, rendering data entirely inaccessible and causing widespread script timeouts.

Response: Node operator verifies HTTP/HTTPS reachability of the canonical URL from external, global networks.

"The Global cache is not receiving any data since 1 hour" — CRITICAL

Trigger: A specific Global Cache reports a sudden, absolute drop in its overall incoming data ingestion rate across all global centers for sixty consecutive minutes.

Technical causes: Exhausted disk space on the Cache's storage arrays; out-of-memory (OOM) errors killing worker processes; or the Cache's outbound IP block inadvertently blacklisted by origin centers due to aggressive polling.

Impact: Massive — end-users relying on this Cache receive increasingly stale data or encounter HTTP 500/503 errors.

Response: Cache operators check storage metrics, restart worker nodes, inspect networking for packet loss.

4.2 Friction and Rate Limiting Anomalies

"Global cache has > 10 download errors from center in 1h over 6h" — WARNING/ERROR

Severity fluctuates between WARNING and ERROR depending on the breadth of Caches affected.

Trigger: Rolling window function detects persistent, repeating HTTP 4xx or 5xx error codes when Caches attempt to fetch data payloads from a specific Node's data server.

Technical causes (multifaceted):

  • Node's data server applying overly aggressive rate-limiting → HTTP 429 Too Many Requests
  • Node's server under-resourced, experiencing intermittent gateway timeouts (HTTP 504)
  • Rapid data deprecation — Cache receives HTTP 404 Not Found because physical data files are deleted by local cleanup scripts faster than Caches can retrieve them

Impact: Partial data loss and high latency. A significant percentage of data is permanently lost during error windows, leading to fragmented meteorological datasets downstream.

Response: Origin Node operator tunes web server rate-limiting logic, scales HTTP server resources, or extends data file persistence windows.

"Global Cache cannot connect to > 10 (or 20) dataservers" — ERROR/CRITICAL

Trigger: Aggregated HTTP connection failures (timeouts, connection refused). The escalation to 20 dataservers triggers CRITICAL.

Technical causes: Compromised network egress at the Cache facility — upstream ISP throttling, internal DNS resolution failures, or an overloaded outbound NAT gateway exhausting ephemeral ports.

Response: Immediate investigation of the Cache's internal DNS resolvers and outbound routing appliances.

5. Protocol, Endpoint & Network Layer Terminations

Beneath the architectural logic of Caches and Brokers lies the fundamental network layer. Monitoring agents continually scrape Global Services for performance telemetry using tools like Prometheus. When the foundational protocols fail, the observability plane goes blind.

5.1 Connection Timeouts and Deadlines

"Timeout: context deadline exceeded" — ERROR

Observed targets: globalbroker.inmet.gov.br, wis2.ncm.gov.sa, wis2-gdc.weather.gc.ca

Trigger: Global Monitor initiates an HTTP GET request (often targeting a /metrics or /prometheus/federate endpoint), but the TCP connection or HTTP response is not completed within the strict timeout window defined by the application's Golang context.Context deadline.

Technical causes: Resource exhaustion — extreme CPU load causing application threads to stall; backend database locking (e.g. PostgreSQL or Elasticsearch) delaying metrics payload assembly; or a stateful firewall silently dropping packets without returning a TCP RST flag.

Impact: Insidious — while actual meteorological data flow and MQTT routing may still function normally, the monitoring plane is effectively blinded. This raises the critical risk of silent, cascading failures occurring without operator awareness.

Response: Monitoring engineers temporarily increase timeout thresholds; target operators optimize computational performance of /metrics endpoints and investigate CPU load averages.

5.2 Abrupt Terminations and Access Denials

"Network Termination: unexpected EOF" — ERROR

Observed target: gc.wis.cma.cn

Trigger: The underlying TCP connection is abruptly severed by the remote server before the complete HTTP payload is transmitted.

Technical causes: Reverse proxy crashed mid-stream due to a segmentation fault; upstream load balancer prematurely killed the connection due to aggressive keep-alive timeouts; or TLS session renegotiation failed, dropping the socket.

Impact: Metric loss and potential instability in actual data fetching, particularly if the same reverse proxy handles both telemetry requests and WNM payload downloads.

Response: Target administrators inspect web server error logs for application panics and review proxy timeout configurations.

"HTTP Error: 403 Forbidden" — ERROR

Observed target: www.wis-jma.go.jp

Trigger: The target server explicitly returns an HTTP 403 status code — successful network connection but deliberate rejection by the application layer.

Technical causes: A Web Application Firewall (WAF) falsely identifying the Global Monitor's User-Agent string or polling frequency as malicious; or incorrectly applied CORS policies.

Response: Target operator updates WAF Access Control Lists (ACLs) to explicitly whitelist known IP ranges of WIS2 Global Monitors.

"HTTP Error: 502 Bad Gateway" — ERROR

The upstream server returned an invalid response, typically indicating the reverse proxy or load balancer cannot reach the backend application.

"Connection Refused" — ERROR

The target server actively rejected the TCP connection, typically indicating the service is not running or the port is not open.

"Network Termination: connection reset by peer" — ERROR

The remote server forcibly closed the TCP connection, often indicating an application crash or resource exhaustion.

"Timeout: i/o timeout" — ERROR

A network-level I/O timeout, indicating packets are not being acknowledged within the expected timeframe.

6. Schema & Metadata Validation Integrity

The operational success of WIS2 relies not just on moving bytes from point A to point B, but on ensuring those bytes are universally comprehensible and discoverable. Data discoverability is strictly governed by compliance with the WMO Core Metadata Profile (WCMP2) and the structural integrity of the WNM schema.

Event TitleSeverityEvent TypeCore System Impact
WIS2 Notification Message not compliant with the defined schema ERROR int.wmo.wis.wme.wnm.validation.schema Message quarantine; downstream schema parsing panics.
Missing Metadata record for data announced in WNM ERROR int.wmo.wis.wme.wnm.validation.metadata Data is "dark" and completely undiscoverable via GDC.
WCMP2 Access Failure ERROR int.wmo.wis.wme.event GDC cannot retrieve mandatory discovery records.
WCMP2 ETS Report (Schema constraint failures) INFO/ERROR int.wmo.wis.wme.event.wcmp2.ets Rejection of non-compliant metadata by catalogues.
WCMP2 KPI Report Degradation WARNING int.wmo.wis.wme.event.wcmp2.kpi Severe penalization in global search rankings.

6.1 Payload and Structural Validation

"WIS2 Notification Message not compliant with the defined schema" — ERROR

Trigger: Global Broker or monitoring tool evaluates the JSON payload against the normative wis2-notification-message-bundled.json schema and detects a structural violation.

Empirical example: data.field properties.content.size exceeds its configured maximum limit (e.g. "should be <= 4096").

Technical causes: Software bugs in the Node's message generation logic; manual formatting errors; or failures to correctly escape complex JSON strings before transmission.

Impact: Immediate and systemic — Global Brokers may quarantine or drop the malformed message. Downstream subscribers executing strict parsing will experience fatal application crashes on deserialization.

Response: Node developers leverage pywis-pubsub or check-jsonschema to pre-validate payloads locally before MQTT publication.

6.2 The Discoverability and "Dark Data" Threat

"Missing Metadata record for data announced in WNM" — ERROR

Trigger: Global Broker receives a WNM containing a specific metadata_id (e.g. urn:wmo:md:uk-metoffice-wmc:weather.prediction...), but cross-referencing with the GDC reveals the record does not exist.

Technical causes: Asynchronous workflows — Node operators deploy new data pipelines and configure MQTT publishers but neglect to publish the accompanying WCMP2 discovery record. Alternatively, the GDC rejected the record during its own ingestion validation.

Impact: Generation of "dark data" — subscribers on the specific topic receive the data, but no new end-users or researchers can discover it via GDC. This violates core WIS2 discovery principles.

Response: Node operator immediately generates a compliant WCMP2 record with the exact metadata_id referenced in the WNM and pushes it to the catalog.

"WCMP2 Access Failure" — ERROR

Trigger: GDC attempts to fetch a referenced metadata record and encounters HTTP 404 Not Found.

Technical causes: Metadata endpoint URL changed without notice, file accidentally deleted, or directory permissions improperly modified.

Response: Operators immediately restore the WCMP2 JSON file to the correct URI path.

6.3 Executable Test Suites and Quality Scoring

"WCMP2 ETS Report" — INFO/ERROR

GDCs deploy automated Executable Test Suites (ETS) for routine evaluation of published WCMP2 records. Results are emitted as INFO telemetry (escalating to ERROR for failures), providing a granular JSON-formatted array of passed and failed constraints.

ETS evaluates: Strict adherence to geospatial bounding box formatting, temporal ISO 8601 syntax, and inclusion of mandatory data policy links.

Impact: If ETS evaluation results in a FAILED code, the GDC outright refuses to ingest the record, rendering the associated data undiscoverable.

Response: Node operators review the specific failed schema constraints and republish the corrected record.

"WCMP2 KPI Report Degradation" — WARNING

Event type: int.wmo.wis.wme.event.wcmp2.kpi

Key Performance Indicators (KPIs) assess the qualitative value of metadata — evaluating the depth and descriptiveness of abstracts, precision of spatial bounding boxes, and completeness of temporal coverage.

If a record passes ETS but scores poorly on the KPI index, a WARNING event is generated. The data is technically valid, but its discoverability ranking in GDC search algorithms will be heavily penalized until the descriptive metadata is enriched.

⚙

7. Systemic Telemetry: Lifecycle Notices & Latent Threats

A holistic observability framework does not solely track failures; it must also account for administrative events and theoretical threats outlined within the architecture's foundational documentation.

7.1 Scheduled Maintenance and Administrative Silencing

Example alerts: "A scheduled maintenance service for CMA Global Monitor", "Maintenance Service for CMA Global Broker"

Though technically administrative notices, these are frequently flagged with CRITICAL severity because they dictate the total (albeit planned) unavailability of a core system component.

Event type: int.wmo.wis.wme.event.notice

Technical causes: SSL certificate rotations, physical infrastructure migrations, emergency hardware upgrades, and significant software transitions (e.g. upgrading a Global Broker's engine to support MQTT v5.0).

Impact: Strictly temporary but highly disruptive if unmanaged. The architecture's redundancy ensures alternative brokers absorb traffic during broker maintenance.

Response: Subscribers relying on a specific Node undergoing maintenance must pause ingestion pipelines or engage failover scripts to source data from alternative regional providers.

7.2 Broker Routing Integrity and Anti-Loop Detection

Global Brokers are mandated to subscribe to each other to ensure redundant and reliable transmission. However, this interconnected mesh introduces the risk of infinite message loops.

Theorized Alert: Anti-Loop Threshold Exceeded

Severity: WARNING or ERROR

Trigger: Duplicate detection heuristic flags an exceptionally high rate of identical UUIDs within a sub-second timeframe.

Technical cause: Failure in the routing logic or a malfunctioning Node entering an infinite retry loop.

Systemic impact if unchecked: Catastrophic — exponential network bandwidth consumption, broker CPU exhaustion, and the eventual crash of the entire PubSub mesh.

Response: Monitoring agents must immediately quarantine the offending Node's topic stream.

Brokers implement an Anti-loop mechanism that tracks message UUIDs and suppresses duplicates.

7.3 Global Discovery Catalogue Latency

Theorized Alert: GDC Metadata Archive Stale (> 24 Hours)

Severity: WARNING or ERROR

Trigger: A GDC's internal synchronization process (e.g. a scheduled harvester pulling records via OGC API endpoints) fails to update its index for a full day.

Technical causes: Backend database hanging (locked indexing queue) or harvester scripts crashing silently.

Systemic impact: The GDC becomes entirely "stale." Users querying the catalogue receive outdated or null results, directly undermining the WIS2 principle of rapid global data discovery.

Response: GDC administrators manually force index rebuilds and inspect harvester application logs.

7.4 The Sensor Centre Paradigm and Performance Thresholds

The most advanced aspect of the WIS2 observability framework. Spearheaded by the WMO's Expert Team on WIS2 Implementation and Transition (ET-W2IT), Sensor Centres act as independent, objective auditing entities distributed across multiple WMO Regions.

Specific deployments:

  • Sensor Centre Global Broker (SCGB)
  • Sensor Centre Global Cache (SCGC)
  • Sensor Centre Global Discovery Catalogue (SCGDC)

These Sensor Centres are designed to generate WME alerts when operational Key Performance Indicators (KPIs) and Service Level Agreements (SLAs) are breached.

Example: Global Broker KPI Breach

If a Global Broker fails to meet the architectural requirement of processing a minimum of 10,000 messages per second, or if its subscriber capacity breaches 1,000 active connections without dynamically scaling, the Sensor Centre's localized OpenMetrics and Prometheus AlertManager scripts will independently generate and push a CRITICAL WME alert to the global network.

Technical cause: Pure computational or bandwidth exhaustion at the target Global Service facility.

Systemic impact: Allows for proactive identification of service degradation long before it cascades into outright failure or total broker disconnection. Provides the global monitoring community with undeniable, objective telemetry to enforce operational standards.

Extensibility: Regional authorities can deploy bespoke Sensor Centres to validate local regulatory compliance (e.g. GBON or RBON data flow), integrating their findings seamlessly into the overarching WME alerting topic.

8. Actionable Response Framework

The ultimate value of the WME specification is not merely in the generation of complex JSON payloads, but in the operationalization of that telemetry into rapid incident response. Monitoring agents, Global Information System Centres (GISCs), and local Node operators must adhere to a strict response matrix governed by data.severity.

SeverityThreat Profile & Example AlertsImmediate Technical ActionEscalation & Remediation
DEBUG / INFO Non-disruptive. Routine telemetry (WCMP2 ETS Passed, standard heartbeats). No manual intervention. Ingest to time-series databases for long-term SLA reporting. Used by Sensor Centres to tune KPI algorithms and adjust baseline anomaly detection thresholds.
WARNING Degradation of redundancy or creeping friction (Disconnected from one Global Broker, KPI score dipping). Trigger automated localized network diagnostics (traceroute, ping). Verify local TLS certificates. Log a non-urgent ticket for next-business-day review. Investigate underlying ISP jitter or minor JSON metadata omissions.
ERROR Isolated failure affecting specific data sets (WNM schema failure, 403 Forbidden, Missing Metadata). Quarantine the malformed payload. Suspend downstream fetching from the failing center. Alert data provider immediately. Require manual schema correction (check-jsonschema) or WAF ACL whitelisting before unblocking.
CRITICAL Systemic or total blackout (Disconnected from all brokers, Cache 0 bytes ingested, Node target Down). Engage emergency fallback. Reroute subscriber scripts to regional backup Caches and alternative brokers. Page standby operations engineers. Escalate to hardware/ISP level. Extensive postmortem analysis required upon restoration.
✓

9. Conclusion

The WIS2 Monitoring Events (WME) framework represents a highly sophisticated, CloudEvents-driven observability layer that is indispensable for the maintenance and scalability of global meteorological data exchange. The architectural transition from static file transfers to a dynamic, asynchronous PubSub mesh introduces immense complexity — while it decouples producers and consumers, it simultaneously introduces the risk of silent, localized failures that can rapidly cascade into global data blackouts.

WIS2 alerts provide unparalleled, granular diagnostics — ranging from the detection of critical physical infrastructure failures (Node disconnections, HTTP target timeouts) to nuanced, deep-packet inspections of JSON schema violations and metadata non-compliance.

The WMO's forward-looking integration of independent Sensor Centres and automated Executable Test Suites ensures a continuous, objective audit of the network's health. This guarantees that not only is the uptime of the physical network relentlessly tracked, but the integrity, compliance, and ultimate scientific discoverability of the meteorological data itself remain entirely uncompromised.

For infrastructure operators and monitoring agents, the continuous ingestion, automated parsing, and rapid operationalization of these WME alerts are paramount to securing the fault-tolerant future of the WMO Information System 2.0.

Incidents

Related alerts are grouped into incidents, enabling collaborative tracking, muting, notes, and activity history.

How Incidents Are Grouped

An incident hash is computed as SHA-256("{title}:{node}"). Alerts with the same title and node share the same incident hash, even if they occur at different times.

Incident Features

FeatureDescription
Node HistoryThe detail page shows all other alerts for the same node, providing context on whether this is an isolated or recurring issue.

CommentsAgents can add comments to an incident. Visible in the activity timeline.
Pinned NotesTimed notes that appear as a banner at the top of the detail page. Useful for marking an incident as "being investigated".
Activity TimelineA chronological log of all actions: comments, emails sent, notes added/removed, muting/unmuting, and page views.
