A reference for the WIS2 Monitoring Events (WME) framework covering infrastructure diagnostics, schema validation, systemic telemetry, and response strategies.

1. Introduction

The WMO Information System 2.0 (WIS2) replaces the legacy GTS file-exchange model with a globally distributed Publish/Subscribe architecture built on MQTT and CloudEvents.

Core infrastructure components — Global Brokers (message routing), Global Caches (payload hosting), and Global Discovery Catalogues (metadata querying) — form a synergistic network that enables real-time diagnostic telemetry.

Performance Mandates

Global Brokers must achieve 99.5% availability, process 10,000+ messages/sec, and support hundreds of concurrent WIS2 Nodes.

The WME specification uses CloudEvents encoded in JSON, broadcast on monitor/a/wis2/#. Agents subscribe to channels like monitor/a/wis2/+ (all centers) or monitor/a/wis2/ca-eccc-msc/# (center-specific).

2. WME Architecture

WMEM payloads are bounded to 8,192 bytes per wis2-notification-message-core.

Severity Levels

SeverityMeaningActions
CRITICAL Total blackout — disconnected from all brokers, cache receiving zero bytes, target endpoint down. Emergency fallback, reroute to backup, page standby engineers, escalate to hardware/ISP.
ERROR Isolated failure — WNM schema failure, HTTP 403/502, missing metadata, connection refused. Quarantine payload, suspend fetching, alert provider, require schema correction.
WARNING Degradation — disconnected from one broker, KPI dipping, download errors. Automated diagnostics (traceroute, ping), verify TLS, log non-urgent ticket.
INFO Non-disruptive telemetry — ETS passed, heartbeats, metadata reports. Ingest to time-series for SLA reporting, tune KPI baselines.

3. Node Connectivity & Broker Disconnections

Nodes must maintain continuous MQTT connections to multiple Global Brokers. Redundant mesh ensures WNMs route through alternative paths during localized outages.

EventSeverityTypeImpact
Disconnected from one Global BrokerWARNINGwme eventRedundancy degradation, no data loss.
Disconnected from multiple Global BrokersERRORwme eventSevere redundancy loss, elevated latency.
Disconnected from all Global BrokersCRITICALwme eventComplete notification blackout.
Target is downCRITICALwme eventEndpoint entirely unreachable.

3.1 Redundancy Degradation

Disconnected from one broker — WARNING

Trigger: Heartbeat dropped from one broker while active on others.

Causes: Transient routing anomalies, firewall misconfigurations blocking port 8883 (MQTTS) or 443 (WSS), TLS handshake failures.

Impact: Negligible — redundancy ensures WNMs publish via remaining brokers.

Response: Review outbound firewall rules, diagnostic packet tracing.

Disconnected from multiple brokers — ERROR

Trigger: Simultaneous drops across two or more (but not all) brokers.

Causes: Regional backhaul outages, BGP route flapping, message queue client resource starvation.

Impact: Increased latency, close to total blackout.

Response: Escalate to Node operator's network team — inspect edge router stability, CPU utilization.

3.2 Total Isolation

Disconnected from all brokers — CRITICAL

Trigger: Absolute silence — zero active MQTT connections.

Causes: Facility power loss, ISP isolation, TLS certificate expiration, messaging software crash.

Impact: No WNMs published — the Node's real-time contribution is erased.

Response: Out-of-band communication, emergency restarts, physical connectivity verification.

Target is down — CRITICAL

Example targets: wis2.ncm.gov.sa:443, www.wis-jma.go.jp:443

Trigger: HTTP GET health checks or ICMP pings receive no response.

Causes: Reverse proxy crash, DDoS mitigation blackholing traffic, server hardware failure.

Response: Verify load balancers, web server daemons, physical server availability.

4. Global Cache & Data Flow Disruptions

Global Caches download payloads from origin Nodes and serve end-users, shielding origin Nodes from bandwidth overload. Cache anomalies mean data is announced but physically unobtainable.

EventSeverityTypeImpact
No cache receiving data from center (6h)ERRORevent.item.downloadGlobal "ghosting" — data announced but inaccessible.
No data received from center (6h)WARNINGevent.item.downloadPossibly localized cache failure or slow production.
Global cache not receiving any data (1h)CRITICALevent.item.downloadCache-wide ingestion failure, broad staleness.
Cache >10 download errors from center (1h over 6h)WARNING/ERRORevent.item.downloadHigh friction fetching, partial payload loss.
Cache cannot connect to >10 (or 20) dataserversERROR/CRITICALevent.item.downloadCache egress failure.

4.1 The "Ghosting" Phenomenon

No cache receiving data — ERROR

Trigger: 6-hour window with WNMs published but zero bytes ingested by any Cache.

Causes: HTTP links in WNMs point to inaccessible servers — NAT firewalls, DNS misconfigured, HTTP daemon crashed while MQTT publisher continues running.

Impact: Subscribers receive notifications but download attempts hit dead links.

Response: Verify HTTP/HTTPS reachability of canonical URLs from external networks.

Cache not receiving any data (1h) — CRITICAL

Trigger: Sudden absolute drop in ingestion rate for 60 consecutive minutes.

Causes: Exhausted disk space, OOM killing workers, outbound IP blacklisted by origin centers.

Response: Check storage metrics, restart workers, inspect for packet loss.

4.2 Rate Limiting Anomalies

Download errors from center — WARNING/ERROR

Causes: Over-aggressive rate-limiting (HTTP 429), gateway timeouts (504), rapid data deprecation (404 from cleanup scripts deleting files faster than Cache retrieval).

Response: Tune rate-limiting, scale HTTP server resources, extend data file persistence windows.

Cache cannot connect to >10/20 dataservers — ERROR/CRITICAL

Causes: Compromised network egress at Cache — upstream ISP throttling, internal DNS failure, overloaded NAT gateway exhausting ephemeral ports.

Response: Investigate DNS resolvers and outbound routing appliances.

5. Protocol, Endpoint & Network Layer Terminations

When foundational protocols fail, the observability plane goes blind — actual data flow may continue while monitoring is compromised.

5.1 Connection Timeouts

Timeout: context deadline exceeded — ERROR

Observed targets: globalbroker.inmet.gov.br, wis2.ncm.gov.sa, wis2-gdc.weather.gc.ca

Trigger: HTTP GET request to /metrics or /prometheus/federate does not complete within the Go context.Context deadline.

Causes: CPU exhaustion stalling threads, database locking delaying metrics assembly, stateful firewall silently dropping packets (no TCP RST).

Impact: Monitoring plane blinded — silent cascading failures risk occurring without operator awareness.

5.2 Abrupt Terminations & Access Denials

Unexpected EOF — ERROR

Target: gc.wis.cma.cn. TCP severed before complete HTTP payload transmitted.

Causes: Reverse proxy segfault, premature keep-alive timeout, TLS renegotiation failure.

HTTP 403 Forbidden — ERROR

Target: www.wis-jma.go.jp. WAF falsely blocking the Global Monitor's User-Agent or polling frequency.

Response: Update WAF ACLs to whitelist Global Monitor IP ranges.

HTTP 502 Bad Gateway — ERROR

Reverse proxy or load balancer cannot reach the backend application.

Connection Refused — ERROR

Service not running or port not open.

Connection reset by peer — ERROR

Remote server forcibly closed TCP — often application crash or resource exhaustion.

I/O timeout — ERROR

Network-level I/O timeout — packets not acknowledged within expected timeframe.

6. Schema & Metadata Validation

WIS2 success requires bytes that are universally comprehensible and discoverable — governed by WCMP2 compliance and WNM schema integrity.

EventSeverityTypeImpact
WNM not compliant with schemaERRORwnm.validation.schemaMessage quarantine, downstream parsing panics.
Missing metadata record for WNM dataERRORwnm.validation.metadata"Dark data" — undiscoverable via GDC.
WCMP2 Access FailureERRORwme eventGDC cannot retrieve discovery records.
WCMP2 ETS Report (constraint failures)INFO/ERRORevent.wcmp2.etsNon-compliant metadata rejected by catalogues.
WCMP2 KPI DegradationWARNINGevent.wcmp2.kpiPenalized in global search rankings.

6.1 Payload Validation

WNM not compliant with schema — ERROR

Trigger: JSON payload violates wis2-notification-message-bundled.json.

Example: data.field properties.content.size exceeds 4096 byte limit.

Response: Use pywis-pubsub or check-jsonschema to pre-validate payloads before publication.

6.2 "Dark Data" Threat

Missing metadata record — ERROR

Trigger: WNM references a metadata_id that doesn't exist in the GDC.

Causes: Async workflows — new data pipelines configured but WCMP2 record never published.

Impact: Data is "dark" — discoverable by subscribers on the topic but invisible to new users via GDC.

WCMP2 Access Failure — ERROR

GDC encounters HTTP 404 when fetching a referenced metadata record.

6.3 ETS & KPI Scoring

WCMP2 ETS Report — INFO/ERROR

GDCs deploy automated Executable Test Suites to evaluate WCMP2 records. Results emitted as INFO (escalating to ERROR for failures). A FAILED code causes GDC to refuse ingestion.

WCMP2 KPI Degradation — WARNING

KPIs assess metadata quality — abstract depth, spatial bounding box precision, temporal completeness. Poor scores penalize discoverability ranking until enriched.

7. Systemic Telemetry: Lifecycle & Latent Threats

A holistic observability framework tracks not just failures but also administrative events and theoretical architectural threats.

7.1 Scheduled Maintenance

Example alerts: "A scheduled maintenance service for CMA Global Monitor"

Often flagged CRITICAL because they indicate planned unavailability of a core component.

Event type: int.wmo.wis.wme.event.notice

Causes: SSL rotations, infrastructure migrations, hardware upgrades, software transitions.

Response: Pause ingestion pipelines or engage failover to alternative regional providers.

7.2 Anti-Loop Detection

Brokers subscribe to each other for redundancy. This introduces infinite message loop risk.

Theorized Alert: Anti-Loop Threshold Exceeded

Severity: WARNING / ERROR

Trigger: Duplicate detection flags high rate of identical UUIDs within sub-second window.

Impact if unchecked: Exponential bandwidth consumption, broker CPU exhaustion, PubSub mesh crash.

Response: Immediately quarantine the offending Node's topic stream.

7.3 GDC Metadata Latency

Theorized Alert: GDC Metadata Archive Stale (>24h)

Severity: WARNING / ERROR

Trigger: GDC's harvester fails to update its index for a full day.

Causes: Database locking, silent harvester crashes.

Response: Manual index rebuilds, inspect harvester logs.

7.4 Sensor Centres

Independent auditing entities deployed by the WMO ET-W2IT team. Three deployments:

  • Sensor Centre Global Broker (SCGB)
  • Sensor Centre Global Cache (SCGC)
  • Sensor Centre Global Discovery Catalogue (SCGDC)

Generate WME alerts when operational KPIs and SLAs are breached.

Example: Global Broker KPI Breach

If a Global Broker fails to process 10,000 messages/sec or exceeds 1,000 active connections without scaling, the Sensor Centre generates a CRITICAL WME alert independently.

Regional authorities can deploy bespoke Sensor Centres to validate local regulatory compliance (GBON/RBON data flow).

8. Actionable Response Framework

The WME specification's value lies in operationalizing telemetry into rapid incident response. Agents must adhere to a strict response matrix governed by data.severity.

SeverityThreat ProfileImmediate ActionEscalation
INFO Routine telemetry — ETS passed, heartbeats. No manual intervention. Ingest for long-term SLA reporting.
WARNING Degradation — broker disconnect, KPI dipping. Automated diagnostics, verify TLS. Non-urgent ticket, investigate ISP jitter.
ERROR Isolated failure — schema failure, 403, missing metadata. Quarantine payload, suspend fetching, alert provider. Manual correction (check-jsonschema) or WAF whitelisting.
CRITICAL Total blackout — all brokers disconnected, cache 0 bytes, target down. Emergency fallback, reroute to backups, page standby engineers. Escalate to hardware/ISP, postmortem upon restoration.

9. Conclusion

The WME framework represents a CloudEvents-driven observability layer indispensable for WIS2 scalability. The transition from static file transfers to asynchronous PubSub introduces complexity — while it decouples producers and consumers, it introduces risk of silent localized failures cascading into global data blackouts.

WME alerts provide granular diagnostics from physical infrastructure failures to deep-packet JSON schema inspections. The WMO's Sensor Centres and automated ETS ensure continuous objective auditing of both network uptime and the integrity, compliance, and scientific discoverability of meteorological data itself.

The WNM is a GeoJSON Feature object per the WMO WNM specification (Manual on WIS, Vol II, Appendix E).

Errors

String errors: Plain text (e.g. "unexpected EOF, collection time 2026-06-18T05:36:35Z").

Object errors: Key-value pairs where each value is a string or array of strings. Truncated to 5 items.

Display: red left border in detail view. Strings shown as-is; objects rendered as label/value rows.

Tests (ETS)

WCMP2 Evaluation and Test Suite results assessing metadata compliance.

FieldTypeDescription
idStringTest URI (e.g. http://wis.wmo.int/spec/wcmp/2/conf/core).
nameStringHuman-readable name (alternative to id).
status / codeStringPASSED, SUCCESS, FAILED, ERROR, SKIPPED.
messageStringDetailed result or failure reason.
StatusMeaning
PASSED / SUCCESSTest completed. Requirement met.
FAILED / ERRORTest did not pass. Requires investigation.
SKIPPEDNot executed — preconditions not met.

Summary

Aggregated test result counts: PASSED, FAILED, SKIPPED, WARNING (all integers).

An ETS report has an issue if total ≠ PASSED. On the dashboard, reports with issues show yellow or red borders.
